# NetBird for Home Assistant v0.2.0 monitoring design

## Context

Version 0.1.0 proves the Cloud authentication, shared peer polling, dynamic peer lifecycle, diagnostics, and release pipeline. It exposes too little of the documented peer response to be useful for day-to-day NetBird monitoring. The client already normalizes IP, last login, SSH, ephemeral, and accessible-peer fields, but the Home Assistant platforms discard them.

NetBird has also replaced legacy Routes with Networks, Resources, and Routers. Version 0.2.0 will add the current read-only topology model without adopting deprecated Routes or any management actions.

## Goals

- Make every peer device operationally useful from its Home Assistant device page.
- Preserve one peer API request per peer refresh.
- Add isolated, rate-aware monitoring for Networks, Resources, and Routers.
- Keep stable entity and device identities through upgrade and reload.
- Provide a universal dashboard that discovers NetBird entities without generated entity IDs or third-party dashboard cards.
- Keep config-entry diagnostics redacted.

## Non-goals

- Legacy `/api/routes` monitoring.
- Write operations, services, buttons, or switches that change NetBird state.
- Traffic, reachability, latency, DNS, policy, billing, or audit-log monitoring.
- Self-hosted endpoint support.
- Serial number, user ID, public connection IP, geographic location, or raw API payload exposure.

## Peer model

The existing peer coordinator remains authoritative and continues polling `GET /api/peers` every 60 seconds. No per-peer API requests are added.

### Enabled entities

| Platform | Key | State source | Category |
| --- | --- | --- | --- |
| Binary sensor | `connected` | `connected` | Primary |
| Sensor | `last_seen` | `last_seen` | Primary |
| Sensor | `ip_address` | `ip` | Diagnostic |
| Sensor | `accessible_peers` | `accessible_peers_count` | Diagnostic |
| Sensor | `last_login` | `last_login` | Diagnostic |
| Binary sensor | `ssh_enabled` | `ssh_enabled` | Diagnostic |
| Binary sensor | `ephemeral` | `ephemeral` | Diagnostic |
| Binary sensor | `login_expired` | `login_expired` | Diagnostic problem |
| Binary sensor | `approval_required` | `approval_required` | Diagnostic problem, conditional |

`approval_required` is created only when the API supplies the field. Missing optional values remain unavailable or unknown and never become a false `off` state.

### Optional entities disabled by default

- IPv6 address.
- Hostname.
- DNS label.
- Operating system.

The peer device retains NetBird as manufacturer and client version as software version. Stable unique IDs remain `<account_id>:<peer_id>:<key>`.

Each integration entity exposes one stable `netbird_key` attribute. The attribute contains only its semantic key and lets the universal dashboard find entities without depending on localized entity IDs. No API values are copied into helper attributes.

## Existing-install migration

The integration version becomes 2 and adds an `async_migrate_entry` path.

For registry entities disabled by the integration itself, migration enables `last_seen` and other newly promoted v0.2.0 entities. User-disabled entities remain disabled. Existing unique IDs and device identifiers do not change.

## Topology API and coordinator

The client adds documented read-only methods for:

- `GET /api/networks`
- `GET /api/networks/{networkId}/resources`
- `GET /api/networks/{networkId}/routers`

A separate topology coordinator polls every 300 seconds. A failed topology refresh does not affect peer entities. A failed peer refresh does not erase the last topology snapshot.

After retrieving the network list, resource and router requests use a shared semaphore with a concurrency ceiling of 6. One topology refresh uses `1 + 2N` requests for `N` networks. Cancellation propagates normally.

The topology snapshot stores each network independently. Failure of a nested resource or router request marks only that part of that network unavailable; successfully returned networks and sections remain usable. Failure of the top-level network list makes all topology entities unavailable while retaining the previous snapshot.

## Topology devices and entities

### Account device

The existing account device gains:

- Total networks.
- Total resources.
- Enabled resources.
- Total routers.
- Enabled routers.

These totals are available only when every contributing topology section succeeded. Partial results are never presented as complete totals.

### Network device

One device is created per network with identifier `<account_id>:network:<network_id>`. It exposes:

- Total resources.
- Enabled resources.
- Total routers.
- Enabled routers.
- Connected routing peers.

Connected routing peers are computed by cross-referencing router peer IDs with the peer coordinator. The value is unavailable when peer data or router data is unavailable. Router groups that cannot be resolved to concrete peers are excluded from the connected count and documented as such.

### Resource device

One device is created per resource with identifier `<account_id>:network:<network_id>:resource:<resource_id>`. It exposes:

- Enabled binary sensor.
- Address sensor.
- Type sensor.

The resource device is linked to its network through `via_device`. Its name comes from the API resource name. Missing optional descriptions or groups create no extra entities.

Topology entity IDs use stable API IDs. Dynamic creation follows the existing coordinator-listener pattern. Removal uses the same conservative ownership checks as peer cleanup, with separate known-ID sets and absence counters.

## Dashboard

`examples/netbird-dashboard.yaml` is replaced with a standard Home Assistant Markdown dashboard. It uses `integration_entities("netbird")`, `device_id`, `device_entities`, and the stable `netbird_key` attribute.

The dashboard contains:

- Account overview with connected peers and topology totals.
- Peer table with name, connection status, IP, last seen, last login, accessible peers, SSH, ephemeral, login-expired, and approval-required values.
- Network table with resource and router totals plus connected routing peers.
- Resource table with name, enabled state, address, type, and parent network.

The dashboard uses no fixed entity IDs and no third-party frontend dependencies. Missing entities render as an em dash. Unavailable data is visibly different from false or zero.

## Privacy and Recorder behavior

Peer IP, hostname, DNS label, operating system, and resource address become Home Assistant entity states only when their entities are enabled. Home Assistant may retain those states according to Recorder configuration. README documentation must state this clearly.

Config-entry diagnostics remain aggregate-only. They may include counts and coordinator success/error classes, but never peer IDs, names, IPs, hostnames, resource addresses, network names, tokens, private URLs, or raw payloads.

## Error semantics

- HTTP 401 triggers reauthentication.
- HTTP 403 reports insufficient permissions without treating the token as expired.
- HTTP 429 and transport/server failures leave the relevant coordinator unavailable until a later refresh.
- Invalid required topology structure rejects only the affected request scope.
- Invalid optional timestamps become unknown.
- Empty peer, network, resource, or router lists are valid zero-state snapshots.

## Validation

- API contract tests for network, resource, and router parsing.
- Concurrency and `1 + 2N` request-budget tests.
- Partial topology failure and recovery tests.
- Peer entity state, missing-field, availability, registry, and translation tests.
- Config-entry migration tests preserving user-disabled choices.
- Dynamic topology creation, reload, unload, and conservative removal tests.
- Dashboard YAML parsing plus template fixture rendering for empty, partial, and populated data.
- Ruff check and format check, mypy, full WSL pytest with coverage, hassfest, and HACS validation.
